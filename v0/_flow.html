The portal as it stands today

This is a replica, not a proposal. Every screen below reproduces what Aleron-Web renders right now, including the parts that break the design system, and each screen carries a findings list saying which parts those are. v1 and v2 argue against this map; v0 only records it.

Nine routes, one of them unreachable. The shell is a 56px header and a centred main, so there is no rail, no footer and no persistent patient context. Everything a physician needs to keep in view while they work is re-rendered inside the content area by each Blade file separately, which is why the tab strip that switches between chart sections has four visually distinct variants and why one route has five tabs where the rest have six.

Inside Risk Models: seven sub-tabs, one route

All seven panels mount at once and fetch in parallel; switching a sub-tab is an x-show, not a navigation. None of the seven has a URL, so none can be linked, bookmarked or opened beside another. The five deterministic domains share one panel layout and Systemic has its own.

Inside Care Plan: a two-step wizard, one route

Care Plan is a port of a separate prototype with its own class vocabulary (#cp), its own navigation strip and its own type scale, mounted in the same layout as the rest. Its page nav mixes patient scope and practice scope in one row: Compose note and Notes history are patient-scoped, Practice · Standing orders is not.

Where the same act happens twice

Two surfaces authorize laboratory orders and they enforce different gates. The Care Plan note can sign and send blood orders under one attestation; it cannot transmit a genetics kit at all, because the pre-test counseling gate exists only on Lab Orders. Standing Orders is the practice-level authorization both of them fail closed against, and it is filed inside a patient chart while containing nothing patient-specific.

Path A Sign & send from the note blood only, one attestation Path B Authorize a new order blood and genetics, counseling gate Gate Standing order on file fails closed when unconfigured

What the map shows

  • Nine screens, four routes that matter. Eleven of the fifteen views a physician can reach live under four URLs, switched client side. Nothing below a chart tab can be linked to a colleague.
  • No patient context bar. Six Blade files re-render the same identity block in six slightly different shapes, and all six scroll away with the content.
  • Four tab-strip variants for one control. Inset holder, inset holder with a border, inset holder with square items, and a card holder with a selected surface. They differ only by hand-copied inline styles.
  • The audit face is the interface. Eyebrows, provenance, formulas, order chips, statuses, metadata keys and the whole care-plan wizard run in the mono face the design system retired from product surfaces.
  • Loading is skeletons. Patients renders four bars, every risk domain renders three, and the design system forbids skeletons outright.
  • Gold is spent on a checkbox. The one sanctioned gold detail is the wordmark bar; the care-plan selection box fills with the same token, six times per screen.

Baseline findings

finding Every branch in this map is a tab. There is no task flow anywhere in v0: no queue, no handoff, no state a patient moves through, and no screen that tells the physician what to do next. The product is a set of viewers with an ordering form attached.

finding Trajectory has occupied a tab slot since launch without ever rendering. It is a disabled span with a title attribute, so its explanation is invisible on touch and to a keyboard user.

note The two ordering paths are the sharpest structural finding on the map. Which gates apply depends on which screen the physician happened to be on, and nothing in either interface says the other path exists.

note Standing Orders is a practice-level compliance artifact addressed by a patient-scoped URL. It renders identically for all six patients in the cohort.
