What authorizing an order actually does, and what it does not

Role and Release Matrix v1 section 3 splits this act three ways. The member creates a request by selecting a path, the physician approves it where approval is required, clinical ops coordinate logistics, and the system transmits it. The physician act on this screen is the approval, not the transmission.

Section 2 then closes the loop the other way: order state is logistics visible to the member and results are hidden until release. Signing a result here makes you the reviewing physician on it. It does not make the result visible to Ethan Park, and nothing on this screen can. That happens once, on the release surface, for the whole package.

Which route an order takes is fixed by its type, not chosen, and a single confirmation can span all four endings at once. Only one of them ever asks the physician to leave, and it asks once.

Labs and genetics
Completes here. Placed through Junction and resulted here, with values rather than a scanned report. Junction carries no imaging, no radiology and no referrals, so it is a lab channel and not a general one.
Imaging
Completes here. Signed in your name and transmitted, and the radiologist's report lands in the chart rather than on this screen. Signing and sending are two acts run back to back, so a row can show a signed order that has not gone out.
Referrals
Signed here, transmitted by the practice. Aleron signs a referral in your name and has no way to send one, and no way to learn when your practice sent it from Canvas. The consult note comes back to the chart.
Prescriptions
Needs your signature in Canvas. Aleron writes it one click from signed. The signature is prescriber-only, bound to your prescribing credentials, so it is given there. This is the only handoff in the flow.
Authorization
Under the standing order for the catalog type, and under your name. An order for a test with no configured id is refused, fail closed.
Genetics
Pre-test counseling attestation is enforced on this path. The mobile standing-order rail does not enforce it yet, which is a tracked gap.
Step-up
Confirming a set and signing a result both need a recent re-authentication. A stale session is refused and re-authenticating returns you here.
Patient sees
Logistics and sample state only. Never the values.

What changed, and where it came from

fixed There is no such thing as zero API options for adding an order, and this set kept implying there was. Three order commands, lab, imaging and referral, are published over the plugin command API, and originating any of them creates the order in Canvas as a staged command in a note. That is adding an order through an API. Imaging and referral can then be signed through the same API. A lab order is the constrained one: it cannot be signed from outside, but it can be originated from outside and sent from outside once signed. What has no create is ServiceRequest, which closes the FHIR route and nothing else. Saying "the API" when meaning FHIR is what produced the wrong picture, and it produced it more than once.

finding A trap for whoever implements this. The commit argument on originate() is silently ignored for every order command: the docs list Reason For Visit, Prescribe, Refill, Adjust Prescription, Refer and the Order commands as types that "will ignore this parameter". So originating with commit set does not commit anything, it stages, and a caller who assumes otherwise gets a staged order sitting in a note that nobody has signed, with no error to say so. Two separate research passes on this set disagreed about exactly this line, one reading it correctly and one building a recipe on top of the wrong reading, which is a fair measure of how easy it is to get wrong.

new A Canvas plugin driving the vendor is buildable from documented parts, and it is a different product than this screen. Outbound HTTP exists with a 30 second cap; plugin secrets are first-class and write-only once set; an inbound route with key authentication receives the vendor's result webhook, and a cron handler polls if there is no webhook. The order is charted by originating and committing a lab-order command against the generic partner and never calling send, because the vendor does the transmitting. The results arrive through the lab-report effect. Every step is documented except configuring the vendor as an electronically-ordering Canvas partner, which is not needed under that shape and is not writable from a plugin anyway.

finding It also answers the iframe question, in the direction nobody asked. A layout effect takes a URL to iframe into the Canvas UI, with the URL declared in the plugin manifest and permissions for scripts and same-origin, alongside app-drawer entries, chart tabs, note tabs, docked panes, action buttons and a custom command. Aleron inside Canvas is documented. Canvas inside Aleron is not mentioned anywhere, in either direction, and the single response header that decides it is not published. The staff single sign-on is real and independent of that: SAML 2.0 against the same Microsoft directory Aleron already uses, with no just-in-time provisioning, which is also the unstated cause of the missing-practitioner failure on EMR.

fixed Results can be written into Canvas as real lab data, and an earlier note here said the opposite. The correction matters more than the mistake: the effects module publishes a lab-report effect that creates a report from a plugin, decoupled from its results, no order, no PDF and no values required, with no Health Gorilla dependency. Attaching results takes tests and values with units, a reference range and an abnormal flag, plus LOINC codings, and the first attach commits the report: Canvas then builds the diagnostic report and renders the document itself. So a vendor-placed order can land in the chart as values a second clinician can trend and compare, not as a PDF.

finding Why the earlier note was wrong is worth keeping, because it is the same mistake twice. The data module lists lab reports and lab values with only read operations, and the FHIR endpoints for observations and diagnostic reports are read only or vitals only. All true, and all beside the point: writing happens through effects, which is a different module, and it was never checked. The first version of this misread FHIR as the whole of Canvas; this one misread the data module as the whole of the SDK.

finding Two things this does not settle. Whether a plugin-created report enters the clinician review queue is undocumented, and it decides whether results reach anybody or merely reach the chart. And egress from the plugin sandbox is undocumented: the sandbox page restricts imports, the filesystem and the host, and says nothing about outbound network access or an allowlist. The HTTP helper exists and the docs' own examples call arbitrary external endpoints with it, so the shape is clearly intended, but a lab pipeline should not be committed to on an inference.

new The screen can exist, and the reason it can is not the one given before. The Plugin SDK publishes lab, imaging and referral order commands over HTTP, and Canvas's own guide says the point is to let something outside Canvas write them. But sign() is imaging and referral only: a lab order cannot be signed from outside Canvas. So the act on this screen is the authorization and Aleron owns the transmission through Junction, which is what the screen already claims. The claim is supportable; the earlier note's reasoning for it was not.

fixed The diagnosis-code gap was filed against the wrong system. A diagnosis code is required to send a Canvas LabOrderCommand, and this screen is not that path. On the vendor's own order, icd_codes is optional and documented as being for insurance billing, which a membership programme with no patient billing does not do. So the missing field was never missing here. The billing type that expresses the model is the one where the client is billed, not the patient.

new Four consequences of reading the vendor's order contract rather than guessing at it. The collection methods are a closed set of four and the screen offered three: on-site collection is now there, and for a clinic that draws blood in its own rooms it is arguably the primary one. The ordering physician is a required field on the order, carrying a name and an NPI, with licensed states beside it, so it is named on the card rather than inferred from the session: a physician cannot order for a patient in a state they are not licensed in, and nothing modelled that. An address is captured for every method, not only the shipped ones. And the screening schedule's activation date is the order's own forward-dating, so the cadence is Aleron's and the date is the order's.

finding Three that remain. The order's free-text clinical note caps at 120 characters and the indication runs several hundred, so the reasoning this set captures for defensibility cannot travel to the lab: only a summary can, and nothing decides which summary. A note id is needed for anything that lands in Canvas and no note appears on this screen. And the third has since been closed by the type control: referrals and imaging were absent from a screen called Orders and are now both on it, which matters because imaging is the only type a third party can sign and send end to end.

finding Who carries the result is a product decision this screen assumes without stating. The vendor offers its own physician network, the customer's physicians, or a hybrid where it validates the order and the customer validates the results. This set assumes the second everywhere, which puts result validation and follow-up on Dr. Okafor with one documented backstop: critical results notify the vendor's network whichever model is chosen. That backstop appears nowhere in these designs, and it is the kind of thing a physician should be told exists.
