What Canvas owns, what Aleron owns, and where the seam is

Canvas is the system of record. Aleron does not mirror the chart and does not try to: allergies, medications, the full problem list and the order history live there, and this screen deep links rather than duplicating. What Aleron owns is the packet, the engine run, the action map state, the clinical plan draft and the release package, none of which Canvas has a place for.

The seam is the write, and it is two seams rather than one. A locked note and the problem-list decisions are written straight into Canvas. An order is not, and it is not read back either: Junction places it, and Canvas has no way to receive it as an order. The chart gets the results and the requisition; the order itself lives in Aleron and at the vendor. Section 7 of the role matrix then makes the link a release precondition: patient visibility opens only after both the Aleron release authorization and the required Canvas linkage are satisfied, unless a separate Aleron-only pilot release is explicitly approved. A write that failed soft is therefore not a cosmetic problem, and it belongs on a screen rather than in a log.

What changed, and where it came from

fixed Results can be written into Canvas as real lab data, and an earlier note here said the opposite. The correction matters more than the mistake: the effects module publishes a lab-report effect that creates a report from a plugin, decoupled from its results, no order, no PDF and no values required, with no Health Gorilla dependency. Attaching results takes tests and values with units, a reference range and an abnormal flag, plus LOINC codings, and the first attach commits the report: Canvas then builds the diagnostic report and renders the document itself. So a vendor-placed order can land in the chart as values a second clinician can trend and compare, not as a PDF.

finding Why the earlier note was wrong is worth keeping, because it is the same mistake twice. The data module lists lab reports and lab values with only read operations, and the FHIR endpoints for observations and diagnostic reports are read only or vitals only. All true, and all beside the point: writing happens through effects, which is a different module, and it was never checked. The first version of this misread FHIR as the whole of Canvas; this one misread the data module as the whole of the SDK.

finding Two things this does not settle. Whether a plugin-created report enters the clinician review queue is undocumented, and it decides whether results reach anybody or merely reach the chart. And egress from the plugin sandbox is undocumented: the sandbox page restricts imports, the filesystem and the host, and says nothing about outbound network access or an allowlist. The HTTP helper exists and the docs' own examples call arbitrary external endpoints with it, so the shape is clearly intended, but a lab pipeline should not be committed to on an inference.

fixed Junction is the ordering channel, so there is no Canvas order record to reconcile. Both order rows said ServiceRequest, read back, not written, which was this table's second wrong answer about the same two rows. ServiceRequest is read only, and the one documented effect that records an externally placed lab order, HealthGorillaLabOrderIngest, is Health Gorilla only: its skip-send marker field is mandatory and Health Gorilla specific. Junction is not a documented Canvas lab partner. So a Junction-placed order produces nothing in Canvas to read back, and the rows now say so. What the chart can carry is the results and the requisition, both of which the API does accept.

finding A clinician working in Canvas will not see a pending Aleron order. That is the cost of owning the channel, and it is a clinical question rather than an integration detail: a second physician opening this chart in Canvas sees results arriving with no order behind them. The nearest documented approximation is to stage a LabOrderCommand through CommandAPI against a lab partner with electronic ordering disabled, so Canvas holds the order and never tries to send it. Every part of that is documented; the combination is not, and it needs confirming with Canvas rather than drawing.

fixed There was no way to log out, and no way to tell who was logged in. .prail__patient names the patient, so across 21 screens nothing said whose session this was and nothing ended it. v0 has both in its header, Dr. A. Okafor beside a Log out button, and the proposals dropped them when the header became a rail. A clinical surface that cannot say who is signed in cannot be handed to the next physician at the same workstation, which is the ordinary case in a clinic. The rail foot now carries the actor and the way out, under a rule, at the bottom where the least frequent act belongs. Proposed in section B as a domain.chart-rail addition, using the foot's existing exemption for a non-section action rather than claiming a new one.

fixed As bare underlined text the control was 15px tall, for the one act that ends the session. A text link is the sanctioned shape where a filled control will not fit, per register O5's fallback, but the hit area still has to be real: the label keeps its size and the target grew to 32px, with the same pointer: coarse guard the row-density variant uses restoring the full 44px floor on touch. Measured 14.35:1 flight-deck and 5.34:1 day.

fixed The reconciliation table keeps what landed and drops how the API is shaped. Which resource and which state are what a physician acts on, because a failed write is theirs to chase. Two of the four go through the FHIR API, create only, never updated and neither accepts a create through the API are not: they are how an engineer diagnoses it. The facts stay recorded here in the annotations and in BRIEF.md.

fixed Lab Order Authorization is not a Canvas resource. The reconciliation table listed it in the Canvas resource column for both order rows, and the seam disclosure named it as a thing Aleron writes. No such resource exists, and the real one cannot be written either: ServiceRequest covers lab, imaging and referral orders and is read and search only in the Canvas FHIR API. Both rows now name ServiceRequest, say read back, not written, and attribute the placement to a Canvas order command. Verified at docs.canvasmedical.com/api/servicerequest.

fixed A matched Condition cannot be updated. The row said Z15.09 matched an existing condition and was updated, not duplicated. The only Condition update the API accepts is marking one entered-in-error, so an update in any other sense is not available. The row now says the existing condition was assessed by an Assess command, which is how v3 already models the same act.

new Two write paths, named separately. The disclosure used to say "the seam is the write" as though there were one. There are two: the FHIR API from outside, which takes a DocumentReference and a Condition, and the Plugin SDK inside Canvas, which is the only way an order or a Goal gets created. A screen that says "written to Canvas" without saying which path is not specifying anything, which is how the invented resource survived this long. The rule is now in BRIEF.md.

finding The genetics row's failure mode changes shape. It read as a skipped write; it is a command that never ran for want of a Canvas practitioner id, which means nothing exists in Canvas to read back at all. Still soft, because the order transmitted to the vendor and resulted, but the recovery is different: attribution has to be resolved before the order can be represented in the chart, not merely re-pushed.
