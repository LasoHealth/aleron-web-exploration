What Canvas owns, what Aleron owns, and where the seam is

Canvas is the system of record. Aleron does not mirror the chart and does not try to: allergies, medications, the full problem list and the order history live there, and this screen deep links rather than duplicating. What Aleron owns is the packet, the engine run, the action map state, the clinical plan draft and the release package, none of which Canvas has a place for.

The seam is the write, and it has two shapes rather than three. Almost everything is a command inside a note: the problem-list decisions, the lab order, the imaging order, the referral and the prescription all sit in one note, and that note is the order history. Aleron signs the imaging order and the referral, sends only the imaging order, and cannot sign the prescription at all, so that one waits here for the prescriber. The second shape is a document filed onto the chart, which is how the vendor's requisition gets there. Lab results are neither: they arrive as values with their units and reference ranges, so a second clinician can trend them. Section 7 of the role matrix then makes the link a release precondition: patient visibility opens only after both the Aleron release authorization and the required Canvas linkage are satisfied, unless a separate Aleron-only pilot release is explicitly approved. A write that failed soft is therefore not a cosmetic problem, and it belongs on a screen rather than in a log.

What changed, and where it came from

fixed The prescription carve-out was right and had never been given a reason. Every version of it said sign-off is "a native, prescriber-only act", which is an assertion. The reason is stronger than the assertion: the command has no sign method available from outside, and sending needs the prescriber's Surescripts identifier on file, with EPCS enrolment on top of that for a controlled substance. Those are identity requirements a third-party surface cannot satisfy on someone's behalf, which is why this is not a policy the design chose and could revisit.

new It also over-claimed in the other direction. Never written is too strong: a prescription can be staged into a note from outside, it just cannot be signed there. So the honest line is that Aleron never signs one, not that it never touches one, and there is a real design option this set currently forecloses: stage the prescription so it is waiting in the note for the prescriber rather than leaving them to key it in. That is worth deciding rather than assuming away.

finding Worth recording precisely, because two readings of the same page disagreed and an earlier version of this note settled it wrongly. Prescribe does have a commit action; what it has no external route to is sign, and that is the one the redirect exists for. Its published actions are sign, sign and send, print, make changes while the command is in review, and send once it is committed. originate() then edit() then review() is the reach Aleron has, which lands the prescription one click from signed rather than making the prescriber key it in. Only that much is reachable from outside.

fixed There is no such thing as zero API options for adding an order, and this set kept implying there was. Three order commands, lab, imaging and referral, are published over the plugin command API, and originating any of them creates the order in Canvas as a staged command in a note. That is adding an order through an API. Imaging and referral can then be signed through the same API. A lab order is the constrained one: it cannot be signed from outside, but it can be originated from outside and sent from outside once signed. What has no create is ServiceRequest, which closes the FHIR route and nothing else. Saying "the API" when meaning FHIR is what produced the wrong picture, and it produced it more than once.

finding A trap for whoever implements this. The commit argument on originate() is silently ignored for every order command: the docs list Reason For Visit, Prescribe, Refill, Adjust Prescription, Refer and the Order commands as types that "will ignore this parameter". So originating with commit set does not commit anything, it stages, and a caller who assumes otherwise gets a staged order sitting in a note that nobody has signed, with no error to say so. Two separate research passes on this set disagreed about exactly this line, one reading it correctly and one building a recipe on top of the wrong reading, which is a fair measure of how easy it is to get wrong.

fixed Results can be written into Canvas as real lab data, and an earlier note here said the opposite. Results take tests and values with units, a reference range and an abnormal flag, plus LOINC codings, and Canvas builds the diagnostic report and renders the document itself. So a vendor-placed order lands in the chart as values a second clinician can trend and compare, not as a PDF. And this no longer needs a plugin, which is the newer half of the correction. Both this note and the ordering document's §5.4 routed it through the plugin CREATE_LAB_REPORT effect, on the strength of the operation being absent from the instance's capability statement. It was called anyway: POST /DiagnosticReport/$create-lab-report answers with a complaint about the body, not a missing route, and the scope is granted. An undeclared operation that works is still an operation, so the results row draws as a plain write and the plugin is not on its critical path.

finding Why the earlier note was wrong is worth keeping, because it is the same mistake twice. The data module lists lab reports and lab values with only read operations, and the FHIR endpoints for observations and diagnostic reports are read only or vitals only. All true, and all beside the point: writing happens through effects, which is a different module, and it was never checked. The first version of this misread FHIR as the whole of Canvas; this one misread the data module as the whole of the SDK.

finding Two things this does not settle. Whether a plugin-created report enters the clinician review queue is undocumented, and it decides whether results reach anybody or merely reach the chart. And egress from the plugin sandbox is undocumented: the sandbox page restricts imports, the filesystem and the host, and says nothing about outbound network access or an allowlist. The HTTP helper exists and the docs' own examples call arbitrary external endpoints with it, so the shape is clearly intended, but a lab pipeline should not be committed to on an inference.

fixed Junction transmits the lab order; the note still records it. This annotation used to end at the first half of that sentence, and the table said no Canvas order record twice as a result. ServiceRequest has no create, which closes one route and not the question: LabOrder.originate() stages the order as a command in the note, and per the ordering document's §4.5 that staged command is the chart record even though it is not what transmits. So the blood-panel row now shows a command id and a placement time, and the only row left with nothing in Canvas is the genetics one, which failed before it got there. This also answers the finding that used to sit below: a second physician opening this chart no longer sees results arriving with no order behind them.
