The six conditions that fail release validation

Role and Release Matrix v1 section 6 names them, and any one of them is enough:

  • Any visible recommendation lacks provenance.
  • Any visible clinical value lacks a unit.
  • Any visible item is not present in the reviewed clinical plan.
  • Any draft or raw AI field is included.
  • Any required hold is unresolved.
  • Physician actor or signature semantics are missing.

The second condition is the reason every value in the preview above carries its unit. It is the same P4 rule the instrument follows everywhere else, promoted here into a release gate.

Why three acts instead of one Sign and release

Role and Release Matrix v1 section 3 lists Sign plan, Create lab order request and Release plan as three separate permissions with three different rows, and one of them (Release plan) carries a delegation clause the other two do not. Collapsing them into one control would make the surface claim an authority model the backend does not have.

It also matters clinically. An order can transmit before the note is locked, and a note can be locked with orders still pending; both are legitimate and both happen. A single button forces one ordering onto every case and silently performs two acts the physician only consented to one of.

What changed, and where it came from

new The order set is a real editable draft, and the draft is a Canvas note. The user story has the physician reviewing, modifying, removing and adding orders, and dispositioning is not editing. Junction settles where the editing has to happen: PATCH /v3/order/{id} accepts exactly one field, activate_by, so nothing is editable after submission and the draft has to precede it. Strict data residency settles where the draft lives: nothing patient-linked sits in Aleron (audit Part 5, decision 2). What is left is a Canvas note holding staged, uncommitted commands. CREATE_NOTE at the start of the cycle, each proposed order originated as a staged command, edit() to modify one, delete() to remove one, another originate() to add one. So the rail now offers Edit this order and Remove, with a reason where it offered Modify and Reject, and the note band says what staged means.

new Note creation is drawn. It was undrawn on every screen in the set and everything downstream needs the note_uuid: no command can be originated without one, so the note is the first act of the cycle rather than a consequence of locking. The document now opens with the note band naming the note and its open date, the workbench rail names the same note on every staged change, and act 3's Canvas linkage stops deferring a link it has had since the cycle began.

gap What this costs, stated plainly. Two things follow from putting the draft in the chart. The chart accumulates open notes carrying staged orders, and clinicians working in Canvas will see them, including orders a physician is still deciding about. And the Note API has no state filter, so Aleron cannot list its own drafts back: a physician's open drafts have to be found by an id Aleron holds elsewhere, or not at all. Neither is fixable at the screen; both are the price of decision 2.
