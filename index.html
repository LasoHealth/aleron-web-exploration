Aleron MD · physician surface

Portal wireframes

Three complete, parallel versions of the physician web portal, built as static HTML against the canonical design system's real tokens and components. v0 records what exists. v1 recreates what the canonical documents already designed. v2 is the one to build.

v0 · baseline As it stands today A replica of the shipped Laravel portal, in its own visual language. Not a proposal. This is the thing the other two are argued against. v1 · canonical The reference surface The per-patient chart the canonical documents already built and the physician register already ratified, recreated against the real tokens. v2 · proposed The chart plus the job v1's chart, plus the queue, ordering, release and audit surfaces v0 has and v1 never covered. The buildable target.
One open question, kept separate

v3 · opt-in care plan is a single screen, not a fourth version. It exists to decide one thing: whether the care plan opens empty and the physician adds engine suggestions in, as the shipped portal does, or opens drafted and the physician prunes it, as the canonical build does. Under the second model an engine draft is the default content of a signed legal record unless someone intervenes, which is worth a decision rather than an inheritance. Everything below the document is identical in both.

The argument in one paragraph

The current portal and the canonical reference surface were designed for different halves of the same job, and neither is complete. v0 knows how a physician gets work done: it has a cohort, lab ordering, standing orders, an EMR bridge, a note that locks, and orders that actually transmit. What it does not have is a chart worth scanning. v1 is the opposite: it is a genuinely excellent instrument, with the action map, the evidence ledger, the vitality model and the journal doctrine all worked out, and it cannot place an order, has no queue, and its release button is literally labelled not wired. v2 is not a third design. It is v1's chart with v0's job attached.

How to read these
  • Every screen is a real, self-contained HTML file that links the canonical tokens.css and components.css directly by URL, so nothing here is hand-copied and nothing can silently drift from the design system. The same URL serves the real Hanken Grotesk, so these render in the actual typeface.
  • Every screen carries a version switcher in its top bar. Use it to flip the same screen between v0, v1 and v2 in place. Where a version has no counterpart the pill is struck through rather than hidden, so the gap is legible rather than silent.
  • Every v2 screen ends with an annotation list saying what changed and where it came from: carried names the v0 file a feature was absorbed from, new comes from the reference surface, gap marks a component the design system has not declared yet, and dropped records a v0 capability deliberately not carried, with the reason.
  • v0 is a record, not a proposal. Where the shipped app breaks a design system rule, the replica breaks it too and annotates it. Do not fix v0.
  • All shared chrome lives in one file, physician-chrome.css. Its section B holds the components this surface family needs and components.json v0.5.0 does not declare yet, each one naming the physician-register clause it comes from. Those are the entries ratification would move upstream.

Running these

Open any file directly in a browser. To browse the set with working relative links, run node scripts/serve.js from the repo root and open http://localhost:4173. The screens need a network connection the first time, to fetch the canonical stylesheets and the typeface.
